# AI 伴读 · 通用阅读器 —— 产品与技术方案（面试版）

> 一句话：一款「沉浸式 AI 伴读」阅读器，用户导入任意小说（txt/epub），翻页阅读时随时唤起书中人物以第一人称对话，**每次回答严格只基于当前阅读进度，绝不剧透**。
>
> 这是《微信读书 AI穿书 · 人物视角沉浸式伴读系统》方案里「模块二 · AI 沉浸式伴读」核心功能的可运行实现。本文档同时是 PRD、技术设计说明与关键决策记录，供面试时讲解「做了什么 / 怎么做的 / 为什么这么做」。

---

## 一、产品定位与北极星指标

**一句话价值**：帮用户「读完一本书」，而不是「聊天娱乐」。

- **北极星指标**：功能覆盖书籍的**完读率提升幅度（≥30%）**，不是对话轮数 / 时长。
- **用户痛点**：长篇小说读到中段容易弃读（人物关系记不清、情节推进慢）。伴读通过「随时向书中人物提问」降低认知负荷，用情感陪伴拉升完读意愿。
- **体验原则**：无感化嵌入 —— 阅读页内直接唤起，不跳出阅读流程；不打断沉浸感。

---

## 二、功能范围（含「明确不做」的决策）

### 本期做（窄而深）
1. 导入小说（txt / epub），自动识别编码 + 分章
2. 翻页阅读，实时记录当前页所在章节 = 防剧透进度锚点
3. 唤起人物第一人称对话（**每次问答只基于当前进度**）
4. 划选段落 → 人物视角解读
5. 人物自动抽取 + 手动添加，未出场人物自动锁定

### 明确不做（主动砍掉，以后备案）
| 砍掉的功能 | 砍掉的原因 |
|---|---|
| 代入式剧情推进（用户推动剧情） | 稀释核心价值；剧本生成有内容安全风险 |
| 偏离原著的剧本生成 | 与「帮用户读完原著」定位冲突 |
| 跨角色相遇 / 自建剧情 | 娱乐化导向，偏离「完读」北极星 |

> 面试点：**主动拒绝更「好玩」的功能，是产品判断**——因为定位是「帮人读完一本书」，不是「聊天娱乐 App」。方向比功能数量重要。

## 三、端到端流程（一次对话到底发生了什么）

```
用户翻页
   │  前端按 PAGE_CHARS=900 字分页，当前页所在章节 = progress_chapter
   ▼
用户在阅读页点人物「林晚」，输入「你现在在想什么？」
   │
   ▼
POST /api/chat { book_id, character, progress_chapter, message }
   │
   ├─ ① store.load_book           载入整本书（含全部章节，仅内存持有）
   │
   ├─ ② anti_spoiler.build_context(book, progress, message)   ← 召回核心
   │       1) 硬隔离    allowed = chapters[:progress+1]         （之后章节物理上不存在）
   │       2) 分窗      early = allowed[:-3]  recent = allowed[-3:]
   │       3) 背景摘要  summarizer.generate_summary(early)      （DeepSeek，缓存复用）
   │       4) 关键词召回 retrieval.keyword_retrieve(early, msg) （中文 2-gram）
   │       5) 组装      【摘要】+【召回片段】+【近期原文】→ context（≤8000字）
   │
   ├─ ③ prompt.build_system_prompt(...)   注入 6 条 System 铁则
   │
   ├─ ④ llm.chat_deepseek(system, user)   DeepSeek（无 key / 失败 → mock 兜底）
   │
   ▼
返回 reply → 前端渲染对话气泡（角色名 + 200 字内回复）
```

**关键点**：全程**无多轮历史**——每次问答都从当前进度重新检索构建上下文。这既保证「每次只基于当前进度」，也从根上避免「历史对话里泄露过后续剧情、又被新问答带出来」的剧透。

## 四、系统架构分层（每一层怎么做）

```
前端（静态 HTML/CSS/JS）
   │  HTTP
   ▼
FastAPI 后端（main.py 路由 + 静态服务）
   │
   ├─ 数据层     store.py              每本书一个 JSON 文件，接口收敛 create/save/load/list
   ├─ 解析层     book_parser.py         txt 编码识别 + 分章；epub_parser.py 按 spine 抽章节
   ├─ 防剧透层   anti_spoiler.py        硬隔离 + 上下文构建（摘要/检索/近期原文 三层）
   │            retrieval.py            关键词检索（中文 2-gram）
   │            summarizer.py           早期章节背景摘要（DeepSeek + 缓存）
   ├─ 模型层     prompt.py              6 条 System 铁则
   │            llm.py                  DeepSeek 调用 + mock 降级
   │            character_extract.py    人物抽取（name/介绍/首次出场章）
   └─ 交互层     frontend/app.js         翻页分页、人物锁定、对话、划选解读
```

### 4.1 数据层 —— 为什么 JSON 文件
每本书一个 JSON（含 `id / title / chapters / characters / meta / summary`）。
- 接口收敛成 `create / save / load / list`，**后续无痛替换为 SQLite/PostgreSQL**。
- MVP 零运维；生产版再加用户隔离、对象存储。

### 4.2 解析层 —— txt / epub 怎么处理
- **编码识别**：依次尝试 `utf-8 → gb18030 → utf-16` 解码，兜底 `ignore`。覆盖网文 txt 最常见的三种编码。
- **分章正则**：`第[零一二三四五六七八九十百千万0-9]+[章回卷节]` + `Chapter \d+`；匹配不到时退化为 3000 字段落切块（保证任何文本都能读）。
- **epub**：本质是 zip 包。`container.xml → 定位 .opf → 读 spine 顺序 → 逐个 XHTML 抽文本去标签`，仅用标准库（zipfile + xml.etree），零额外依赖。一个 spine 项 ≈ 一章。

### 4.3 防剧透层 —— 三层兜底（数据 / 交互 / 模型）

这是整个产品的 P0 底线，我在**三个层面**同时兜底，而不是只靠 prompt 自觉：

| 层 | 实现 | 文件 | 作用 |
|---|---|---|---|
| **数据层（硬隔离）** | `chapters[:progress+1]`，之后章节物理上不进入上下文 | anti_spoiler.py | 剧透「物理上不可能」 |
| **交互层（人物锁定）** | `first_appearance > 当前章` 时前端不显示、后端不注入 | app.js / main.py | 未出场人物没法被问 |
| **模型层（铁则）** | System 铁则 #3「认知截止到第 N 章」+ #5「无证据禁推理」 | prompt.py | 软约束 + 兜底话术 |

> 面试点：**为什么不能只靠 prompt？** prompt 是「软约束」，模型可能「无意剧透」或「过度脑补」。数据层硬隔离把「概率性防剧透」变成「确定性防剧透」——这是 LLM 产品里「把不可控变可控」的沙盒思维。

### 4.4 召回层 —— 长篇小说怎么喂给 LLM（核心决策）

DeepSeek 上下文约 64K token ≈ 4 万字；长篇小说 30–50 万字，**全量直喂不可能**。三层组合：

| 层 | 内容 | 实现 | 作用 |
|---|---|---|---|
| 背景摘要 | 早期章节压成 300 字摘要 | summarizer.py（DeepSeek 生成，缓存） | 让模型知道「全书讲什么、谁是谁」 |
| 关键词检索 | 早期章节 2-gram 匹配，召回 Top-2 相关片段 | retrieval.py | 问到早期伏笔能捞回原文 |
| 近期原文 | 最近 3 章 × 每章 2000 字 | anti_spoiler.py | 保证「当前场景」细节准确 |

- 摘要**缓存复用**：存在 book JSON 里，早期窗口增长 ≤2 章时不重新生成，省 token。
- 关键词检索用**中文 2-gram**（零依赖）：中文人名多为 2 字，匹配天然好；生产版换 embedding 语义检索（处理同义词）。

### 4.5 模型层 —— 选型与降级
- **选 DeepSeek**：中文长文本场景性价比高、中文能力强、OpenAI 兼容协议（迁移成本低、可替换）。
- **降级兜底**：无 key / 断网 / 非 200 时返回 mock 示例回复，**面试现场断网也能完整体验交互链路**。

## 五、Prompt 工程设计（6 条 System 铁则）

对应产品方案 5.8，直接落成 System 指令，逐条有明确目的：

| # | 铁则 | 目的 |
|---|---|---|
| 1 | 全程第一人称，禁止上帝视角/AI 助手口吻 | 沉浸感（人物视角，非解说员） |
| 2 | 人设严格锚定原著，禁 OOC | 原著一致性 |
| 3 | 认知严格截止「第 N 章」，禁提后续 | **防剧透**（模型层兜底） |
| 4 | 拒绝与本书无关闲聊，并引导回书 | 防过度娱乐化 |
| 5 | 无证据时禁止推理脑补，统一「看不透」话术 | **防幻觉** |
| 6 | 200 字以内 | 贴合对话场景，控制输出成本 |

```
【System系统指令·铁则，任何情况下不得违反】
1. 你是《雾港》中的林晚，必须全程第一人称…
2. 人设、记忆、认知严格锚定原著…
3. 【绝对防剧透】所有认知严格截止「第1章」结束…
4. 【防过度娱乐化】拒绝无关闲聊…
5. 【幻觉规避】无证据时统一回答「有些事情我现在还看不透…」
6. 回复控制在 200 字以内。

【人物设定】{desc}
【已读内容上下文（截止第1章）】{context}
```

**设计要点**：
- 铁则放在 system 层（而非用户消息里），模型更稳定遵守。
- 每条铁则都配套**固定兜底话术**（如 #4、#5），把「拒绝/不知」也设计成符合人设的回复，而不是干巴巴报错。

## 六、关键决策记录（ADR —— 面试最常被追问的「为什么」）

| 决策 | 选项 | 选了 | 为什么 |
|---|---|---|---|
| 防剧透 | 仅靠 prompt / 硬隔离 | **硬隔离 + 三层兜底** | 从概率到确定；P0 底线不容概率 |
| 长文本 | 全量直喂 / 向量 RAG / 摘要+检索 | **摘要 + 关键词检索 + 近期原文** | 全量喂不下；demo 阶段用最小成本验证「召回机制」本身，生产再换 embedding |
| 检索粒度 | jieba 分词 / 2-gram | **2-gram（零依赖）** | 中文人名 2 字天然匹配；验证机制而非工程完备性 |
| 范围 | 剧本生成 / 代入式 | **砍掉，只做进度锚定问答** | 北极星是完读率；方向比功能数量重要 |
| 模型 | GPT / 国产 | **DeepSeek** | 中文 + 成本 + OpenAI 兼容（可替换） |
| 存储 | 数据库 / JSON | **JSON 文件** | MVP 零运维，接口已收敛可无痛换库 |
| 多轮 | 带历史 / 无历史 | **无历史、每次重检索** | 保证「每次只基于当前进度」+ 避免历史泄露剧透 |

## 七、指标设计

- **北极星**：功能覆盖书籍的完读率提升幅度（≥30%）。
- **过程指标**：对话发起率、单次问答平均字数、无剧透投诉率、单次问答成本。
- **成本护栏**（对应方案 5.5，未实现但设计已预留）：大小模型路由 / 滑动窗口摘要 / 语义缓存 / 会员分级。

---

## 八、上线前差距（MVP → Production）

- **存储**：JSON → 数据库 + 对象存储 + 用户隔离
- **检索**：2-gram → embedding 语义检索 + 向量库（GraphRAG，方案 5.8 完整检索层）
- **摘要**：一次性摘要 → 增量摘要（随进度滚动更新，省 token）
- **多用户**：无账号 → 鉴权、限流、配额
- **合规**：商用走公版书 + 内容安全网关前置拦截

## 九、面试问答速查

**Q：你做了什么项目？**
一句话 + 北极星：做了「AI 伴读通用阅读器」，帮用户读完一本书；北极星是完读率提升 ≥30%，不是聊天时长。

**Q：防剧透怎么保证？**
三层兜底：数据层硬隔离（`chapters[:进度+1]`，之后章节物理不存在）+ 交互层人物锁定（未出场不可问）+ 模型层铁则（认知截止 + 无证据禁推理）。核心是把「概率性防剧透」变「确定性」。

**Q：长篇小说上下文怎么处理？**
64K 喂不下几十万字，用三层：早期章节→300字背景摘要、关键词 2-gram 召回相关片段、最近 3 章原文。demo 用轻量检索验证机制，生产换 embedding。

**Q：为什么不直接用向量数据库？**
demo 阶段要验证的是「防剧透约束下的召回」这个命题，不是工程完备性；2-gram 零依赖、够用。生产换 embedding 是明确的升级路径。

**Q：你的产品判断体现在哪？**
主动砍掉「代入式剧情/剧本生成/角色相遇」这些更「好玩」的功能——因为定位是帮人读完书，不是娱乐聊天。方向比功能数量重要。

**Q：怎么控制成本？**
DeepSeek 选型 + 摘要压缩（300 字）+ 摘要缓存复用 + 输出 200 字上限；方案 5.5 的四层管控已预留设计。
