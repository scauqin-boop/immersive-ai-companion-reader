# Prioritized Feature Roadmap — 微信读书「AI 伴读」demo

> 来源文档：《微信读书_AI穿书_产品方案》作者覃国权（港大）
> 本 Roadmap 服务目标：**1 周内做出可面试演示的 demo**，而非正式上线。评估口径已据此从「生产优先级」调整为「秋招 demo 优先级」。

## Feature Overview

- Total items: 7（仅模块二「AI 沉浸式伴读」；用户已明确「核心模块做深」，模块一/三暂不入 build 范围）
- Strategy focus: 用「防剧透进度锚定角色对话」这个最小闭环，同时承载**产品判断力**（防剧透规则）与**技术深度**（Prompt 铁则 / RAG / 进度硬隔离）两条秋招叙事线
- Decision framework: 加权评分（Weighted Scoring），非 RICE/ICE
- Scoring scale: 1–5，各维度同尺度；Effort 与 Risk 采用反转正分（5=低），详见下

## Evaluation Framework

- Criteria and weights（专为秋招 demo 设定，总和 1.0）:

| 维度 | 权重 | 含义（1–5） | 为什么设这个维度 |
|---|:--:|---|---|
| 用户价值 / 方案核心度 | 0.25 | 5=命中「弃书」核心痛点 | 复用方案 P0 定位 |
| 秋招展示力 | 0.25 | 5=视觉 wow + 可面试讲的完整故事 | demo 的第一目的 |
| 技术/产品深度 | 0.20 | 5=同时体现 AI 工程与 PM 判断 | 「都要兼顾」岗位要求 |
| 开发成本（反转，5=低） | 0.20 | 5=1–2 天可成 | 1 周硬约束 |
| 稳定性/合规（反转，5=低风险） | 0.10 | 5=演示可复现、无合规雷 | 面试现场不能翻车 |

- Framework used: Weighted Scoring（`Score = Σ(score×weight)`，Effort/Risk 已反转，故全部为正向贡献）
- Notes on constraints:
  - **「核心模块做深」×「1 周内」存在张力** → 范围收敛为「最小闭环 + 1 个低成本增色 + 1 个冲刺项」，其余写入后续迭代。
  - 模型接入：真实 LLM API + mock 降级兜底（保证面试现场断网/无 key 也能跑）。
  - 交付形态已升级为「**通用 AI 阅读器**」（2026-08-21 用户新增需求）：支持自行导入任意小说文本 → 翻页阅读 → 在当前页唤起人物对话，进度实时锚定防剧透。《三体》降级为「用户自行导入的示例书」，另内置一份原创示例文本用于验证机制。
  - 正式商用 MVP 仍按方案走公版书规避版权。

## Strategic Insights

- Trade-offs（Top 3）:
  1. **做深 vs 做广**：1 周内宁可只交付 F1+F2+F3 的精致闭环，也不铺三个模块的浅壳——「一个做到精」比「三个都浅」对面试更有利。
  2. **真实 API vs 演示稳定**：真实 API 更有说服力，但面试现场可能断网/限流；选择「真实 API + mock 兜底」牺牲一部分开发时间，换取零翻车。
  3. **关系图谱 vs 实时解读**：同为 F1 的增色项，图谱更炫但更贵，解读更便宜；若时间紧张，砍图谱保解读（保基本盘完整）。
- Dependencies:
  - F1 强依赖 F2（防剧透是对话的前置硬约束，二者本质是一个整体，应合并开发为「防剧透进度锚定视角对话」）。
  - F3/F5 复用 F1 的 API + Prompt 链路，是 F1 的衍生品。
  - F4 依赖「已读进度 + 实体抽取」，可与 F1 并行但要等进度模型定型。
- Portfolio balance（1 周版）:
  - 1 个战略赌注：F1+F2（核心闭环）
  - 1 个 quick win：F3 划选解读（复用链路，便宜）
  - 1 个冲刺项：F4 关系图谱（时间有余才做）
  - 可靠性基建：F2 防剧透硬隔离（本身就是 demo 的「地基」）

## Recommended Roadmap（按「周」而非「季度」）

- **Now（第 1–3 天，必须）**：
  - F1+F2 合并为「防剧透进度锚定视角对话」——选角色（叶文洁/汪淼）→ 切进度 → 第一人称问答 → 剧透/OOC 报错按钮。
  - 落地 Prompt 铁则（System 指令：第一人称、人设锚定、进度硬截止、拒绝闲聊、幻觉兜底话术）。
  - 真实 LLM API + mock 降级兜底。
- **Next（第 4–5 天，quick win）**：
  - F3 划选段落实时解读（复用 F1 链路）。
  - 前端读页 UI 打磨：藏青主色、信笺质感、不遮挡正文（呼应方案「轻量化/无打扰」交互原则）。
- **Later（第 6–7 天，冲刺 / 兜底）**：
  - F4 无剧透关系图谱（时间有余）；否则写进「后续迭代」说明，面试里讲设计思路即可。
  - 沉淀 demo 说明页 + 数据指标口径（复用方案 5.7：北极星=完读率提升，过程=渗透率/留存/分享率）。

> 未纳入 build 但保留在面试叙事里的能力（写进 Roadmap 后续即可，不必实现）：F5 通俗化、F6 倦怠弱提示、F7 音色播客、模块一先导片、模块三复盘/分享。

## 明确不做（范围纪律 / 未来路线）

用户看过「导入短篇 → 自动生成剧本 → 选人物推进甚至偏离原著」这类交互式小说作品，但**明确判断现阶段不做**，理由：它与核心价值「帮用户读完一本书」冲突，会滑向「聊天娱乐」（违背方案 4.2「不是聊天娱乐」+ 5.3「防过度娱乐化」）。

- **核心铁律（现做）**：每次问答只基于当前阅读进度，进度硬隔离防剧透。
- **未来可拓展（不做，仅备案）**：① 代入式剧情推进；② 偏离原著的开放式剧本生成；③ 跨书/跨角色相遇对谈。
- 面试话术价值：主动「say no」+ 用「帮读完书 vs 做游戏」的定位差异讲清取舍。
